## Constats

Aucun constat Bloquant ni Important. Quatre constats Mineurs.

### I-1 (Mineur) : `provider_text` d'un compte en erreur n'a pas de test d'isolation permanent

- Code : `src/core/services/whatsapp-account-service.ts:508` (et colonne `whatsapp_accounts.error_provider_text` des deux pilotes).
- Scénario : le compte de beta passe en erreur avec un message brut de Meta ; ce texte ne doit jamais apparaître dans une réponse d'acme. Le contrat (`packages/contracts/src/whatsapp.ts`, `WhatsAppAccountView.provider_text`) l'affirme implicitement, mais la suite `src/__tests__/isolation/` ne teste que `error_detail` (test « audit R-5 » de `accounts.test.ts`), pas `provider_text`.
- État : sain aujourd'hui. Vérifié par exécution (sonde, SQLite et Postgres) : un marqueur placé dans le `provider_text` de beta n'apparaît dans aucune réponse d'acme (`/whatsapp-accounts`, `/whatsapp-accounts/<id acme>`, `/bots`, `/bots/ventes`, `/bots/ventes/health`, `/auth/me`) ; le résumé du numéro de l'agent IA (`BotNumberSummary.account`) ne porte ni `error_detail` ni `provider_text` ; une vérification réussie remet la colonne à null. Tous les chemins qui écrivent l'état du compte (`setWhatsAppAccountError`, `markWhatsAppAccountVerified`, remplacement des identifiants, déconnexion) écrivent aussi cette colonne, et `reportSendError` (`src/core/handler.ts:427`) l'efface en passant null.
- Test manquant : dans `accounts.test.ts`, un compte de beta en erreur avec un `provider_text` marqueur (via `world.providers.verifyMeta.mockImplementationOnce`), puis `expectNoMarker` sur les vues d'acme, à la manière du test R-5 (règle « un invariant affirmé sans test qui casse »).

### I-2 (Mineur) : la clé `bot.not_found` d'un agent IA d'une autre organisation n'est comparée par aucun test

- Code : `src/api/errors.ts` (`botNotFound`), tests `src/api/admin/__tests__/org-isolation.test.ts:214` (R15) et `src/api/admin/__tests__/bots-routes.test.ts:501`.
- Scénario : le contrat `ERROR_REASONS` (`packages/contracts/src/errors.ts`) affirme qu'une clé ne distingue jamais « tenu par une autre organisation » de « introuvable ». Pour les agents IA, R15 ne compare que le message pour un agent IA d'une autre organisation, et `bots-routes.test.ts:501` ne vérifie la clé que pour un agent IA inexistant. Une évolution qui donnerait une clé différente au cas « autre organisation » (même message) passerait les tests. Les comptes WhatsApp (`errorOf` compare l'erreur entière), les numéros, entités, membres et invitations sont, eux, couverts.
- État : sain aujourd'hui. Vérifié par exécution (sonde, SQLite et Postgres) sur 40 paires de requêtes d'acme (objet de beta contre objet inexistant) : statut, code, message, clé et détails identiques partout, et rien d'écrit chez beta (voir « Tests lancés »).
- Test manquant : dans R15, comparer `res.body.error` entier (hors `request_id`) à celui d'un agent IA inexistant, pour chaque route du tableau ; idéalement étendre la liste aux routes de statut, de liste d'accès limité (y compris liste vide), de débranchement, de santé, de métriques, d'usage et de leads.

### I-3 (Mineur) : les liens d'invitation et de réinitialisation sont journalisés dès que `NODE_ENV` n'est pas `production`

- Code : `src/core/auth/mailer.ts:8` et `:17` (`isProduction`, `writeDevelopmentLink`), exemption `check-logs-ignore` acceptée par la garde.
- Scénario : un lien d'invitation porte le jeton qui fait entrer dans une organisation. Le comportement est sûr par opposition : en production il n'est jamais écrit, mais un déploiement qui oublie `NODE_ENV=production` (aucun Dockerfile ne le fixe aujourd'hui, `docker-compose.yml` ne le définit pas) journalise en clair l'adresse et le lien ; quiconque lit les journaux peut alors rejoindre l'organisation invitante. Ce n'est pas un passage entre organisations par le produit, mais c'est une règle « jamais de jeton dans un journal » qui échoue de façon ouverte.
- Test présent : `mailer.test.ts` vérifie la branche production. Test manquant : aucun ne protège contre un `NODE_ENV` absent. Proposition pour le chantier S : écrire le lien seulement sur un choix explicite (par exemple `NODE_ENV === 'development'` ou une variable dédiée), et refuser le démarrage sans fournisseur d'e-mail hors développement.

### I-4 (Mineur) : le chemin de retour `next` après une session expirée n'est pas lié à l'utilisateur

- Code : `apps/web/src/lib/safe-next.ts:58` (`loginPathFor`), `apps/web/src/components/providers/session-provider.tsx:66`, `apps/web/src/middleware.ts` (redirection avec `next`).
- Scénario : sur un navigateur partagé, la session de l'utilisateur d'acme expire sur `/fr/agents/<identifiant>?…` ; un utilisateur de beta se connecte depuis cette page et est envoyé sur ce chemin. Aucune donnée d'acme n'est servie : le cookie `wab_org` est lié à l'identifiant de l'utilisateur (`readOrg(accessSubject(...))`), l'organisation active est celle de beta, et l'agent IA d'acme répond 404 comme un inconnu (ou c'est un agent IA de beta qui porte le même identifiant). Seule l'adresse (identifiant d'agent IA, paramètres) passe d'un utilisateur à l'autre, ce que l'historique du navigateur montre déjà.
- Vérifié par lecture seulement. Pas de test à exiger ; à garder en tête si une page porte un jour une donnée de contact dans son adresse.

## Vérifié et sain

- 404 indistinguables : 40 paires de requêtes d'acme contre un objet de beta et un objet inexistant, comparées sur statut, code, message, clé et détails, identiques sur SQLite et Postgres (agent IA : lecture, modification, statut, liste d'accès limité vide et non vide, branchement d'un agent IA de beta et d'un numéro de beta, débranchement, activation dans les deux sens, santé, métriques, usage, leads, lead, LLM lu et écrit, CRM lu, écrit et validé, mappings lus et écrits, simulation ; compte WhatsApp : lecture, webhook, renommage, vérification, rafraîchissement, déconnexion, identifiants, numéro de beta via le compte de beta et via le compte d'acme ; entité ; appartenances et statut d'un membre ; relance et révocation d'une invitation ; création d'agent IA, invitation et appartenances avec une entité de beta). Aucune réussite sur un objet de beta, rien d'écrit chez beta.
- Clés de refus : `refusal` (`bot-service.ts`) donne `assign.not_found` au branchement, que le numéro soit absent ou d'une autre organisation, et `bot.not_found` ailleurs ; `validationError` des listes d'accès limité passe avant le store (même 400 pour un agent IA de beta et un inexistant) ; `session.organization_suspended` n'est renvoyée qu'après le contrôle d'appartenance (vérifié par exécution : un non-membre qui vise beta suspendue reçoit exactement le refus d'une organisation inexistante, sans clé).
- `GET /auth/me` et organisations suspendues : seules les organisations où le membre a une appartenance active sont listées (`if (!role) continue`), une organisation suspendue porte `status: 'suspended'`, une organisation supprimée est écartée. Elle n'est jamais ouvrable : `resolveAccess` refuse tout statut autre que `active` (403), avec ou sans en-tête (vérifié par exécution sur cinq routes et une écriture) ; un membre de deux organisations dont une suspendue reçoit 400 « Organisation à préciser » sans en-tête, 403 vers la suspendue, 200 vers l'autre, sans donnée de la suspendue ; les webhooks de l'organisation suspendue ne déclenchent ni LLM ni envoi. Côté web, `isOpenable` filtre `resolveActiveOrg`, `acceptedOrganization`, `POST /api/auth/org` (403) et `clearOrgIfInaccessible` ; le sélecteur et la page Organisations désactivent l'entrée et le disent.
- Liste d'accès limité vide : `checkRoute` relit la liste en base à chaque message et `contactMatchesAllowlist` sur une liste vide renvoie faux, donc `not_allowed` (compteur, aucune session, aucun LLM) ; la relecture avant envoi (`stillServed`) applique la même règle ; le mot-clé « reset » n'est accepté de personne ; aucun autre chemin d'envoi n'existe (recherche de `sendText` et de `checkRoute`). `decideTransition` ne dispense de l'entrée que si le statut stocké, relu dans la transaction, est déjà `limited` ; l'activation garde l'exigence (contrôle ajouté après la transition, annulation de toute la transaction : numéro, liste et statut, tests de `whatsapp-topology.test.ts` sur les deux moteurs).
- `delivery_failures` et `last_delivery_error_code` : lus par `getWhatsAppNumberForBot(clientId, botId)`, écrits seulement par `handleMetaEvents` sur un numéro cherché dans l'inventaire du compte authentifié (`findPresentNumber(account.id, …)`), donc une organisation ne peut pas gonfler le compteur d'une autre avec un webhook qu'elle signe elle-même ; une reprise de numéro crée une nouvelle ligne dans le compte repreneur (compteurs à zéro), l'ancienne passe `removed`. Test d'isolation présent (`accounts.test.ts`, spec §7.6).
- Vue de compte : `error_detail`, `error_cause` et `provider_text` ne sortent que pour un compte en `error` stocké, par une vue réservée à l'admin de l'organisation ; `CANNOT_CONNECT` couvre aussi bien « app tenue ailleurs » que « app du jeton changée », donc `error_cause: 'support'` n'ajoute aucun renseignement sur une autre organisation (test R-5). Ordre des paramètres de `setWhatsAppAccountError` correct sur les deux pilotes.
- Code appelé non modifié par le lot : `src/webhooks/`, `src/core/router.ts`, `src/api/middleware/context.ts`, `src/api/middleware/auth.ts`, `apps/web/src/lib/session.ts` (aucune différence depuis `dd06118`).
- BFF : `engineFetch` n'a changé que par la clé `session.expired` ; l'en-tête d'organisation et le cookie lié à l'utilisateur sont inchangés. Les routes à plusieurs appels (`/api/bots/summary`, `/api/usage/summary`) relisent le cookie à chaque appel, mais la garde de l'organisation affichée (`X-Wab-Org`, 409 `ORG_CHANGED`) empêche de mêler deux organisations dans une réponse : un changement d'organisation en cours de boucle donne des lignes « indisponible », jamais les chiffres d'une autre organisation sous le nom d'un agent IA. `errorResponse` ne relaie que des clés connues de `ERROR_REASONS` et la référence de la requête.
- Notices d'organisation : le nom affiché vient de la session de l'utilisateur lui-même (`prev`, `shown`), relu sans confiance depuis `sessionStorage` (même origine).
- Journaux : garde `check:logs` réussie, une seule exemption (I-3) ; `providerDetail` (Meta, CM.com, CRM) n'est lu nulle part ; plus aucun corps de réponse ni charge utile de message journalisé dans les transports.
